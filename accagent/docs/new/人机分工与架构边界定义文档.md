# SpatialAccAgent 人机分工与框架边界定义文档

## 0. 文档目的

本文档用于定义 SpatialAccAgent 框架中 human、agent、checker/tool 三类角色的职责边界。该文档重点回答以下问题：

1. 在一次 accelerator design run 中，哪些内容由 human 提供？
2. 哪些任务由 agent 自动完成？
3. 哪些结果必须由 checker 或真实工具结果验证？
4. 哪些修改 agent 可以自动执行？
5. 哪些修改必须 human 批准？
6. 哪些行为 agent 永远不能做？

该文档的核心目标是让 SpatialAccAgent 不是一个无约束的硬件代码生成器，而是一个可信的 design closure 框架。

本文档统一采用以下框架定位：

**SpatialAccAgent is a human-guided, agent-executed, checker-verified framework for LLM spatial accelerator design.**

中文含义是：

**SpatialAccAgent 是一个 human 给出目标和边界、agent 执行设计闭环、checker 和工具结果验证正确性的 LLM spatial accelerator 设计框架。**

---

## 1. 框架基本定位

SpatialAccAgent 每次只针对一个明确的目标模型设计一个专用 spatial accelerator。

因此，单次运行不需要 human 给出一组模型范围，也不需要让 agent 判断支持完整模型还是单个 block。每次设计任务已经有一个明确目标，例如：

**为某个指定的 decoder-only LLM block 生成 FPGA spatial accelerator。**

SpatialAccAgent 的目标不是让 agent 自由设计所有东西，而是在 human 给定目标和可信边界之后，让 agent 自动完成复杂工程流程中的设计文件生成、连接、验证、错误定位、修复和回归测试。

更准确地说：

**Human defines the task and trusted boundary. Agent builds and repairs the design within that boundary. Checkers and tool results decide whether each step is valid.**

中文含义是：

**human 定义任务和可信边界，agent 在这个边界内构建设计并修复错误，checker 和工具结果判断每一步是否有效。**

---

## 2. 总体设计原则

SpatialAccAgent 的人机分工应遵循三条原则。

### 2.1 Human 不做低层重复工作

Human 不应该负责手动完成大量低层工程任务，例如：

* 手写所有 Chisel / RTL；
* 手动连接所有 top-level 信号；
* 手动生成所有 testbench；
* 手动整理每个 trace；
* 手动解析每个仿真日志；
* 手动定位每个 wrong address、missing beat、stream mismatch；
* 手动反复运行 regression；
* 手动维护所有 design files 之间的一致性。

这些工作正是 agent 框架需要自动化的部分。

---

### 2.2 Agent 不做无约束设计

Agent 不是一个可以任意修改设计目标、模型语义、数值策略和验证标准的自由设计师。

Agent 必须在以下边界内工作：

* 给定目标模型；
* 给定目标平台；
* 给定数值策略；
* 给定可信模板库；
* 给定设计目标；
* 给定 checker；
* 给定工具链；
* 给定回归测试。

Agent 的每一步动作必须落到显式设计状态中，并且必须由 checker 或真实工具结果验证。

---

### 2.3 Checker 和工具结果是正确性的依据

Agent 可以生成解释、提出假设、给出修复建议，但 agent 的自然语言解释不能作为正确性依据。

正确性的依据必须来自：

* 静态检查；
* stage-level verification；
* top-level verification；
* system-level verification；
* board-level run；
* numeric comparison；
* stream trace check；
* beat count check；
* address map check；
* deadlock check；
* synthesis report；
* timing report；
* resource report；
* regression result。

因此，SpatialAccAgent 的可信性来自：

**explicit design state + executable checkers + real tool results**

而不是 agent 自己说“我认为已经修好了”。

---

## 3. 三类角色

SpatialAccAgent 框架中有三类核心角色：

1. Human designer；
2. Agent system；
3. Checker / tool system。

三者职责不同，不能混淆。

---

## 4. Human 的职责

Human 的职责不是低层实现，而是定义任务、设定边界、批准重大修改和最终确认结果。

### 4.1 给定单次设计任务

每次运行中，human 只需要给定一个明确目标模型，而不是给定模型范围。

Human 需要提供：

* target model；
* target platform；
* numeric policy；
* trusted template library；
* design goal；
* available toolchain；
* existing code or context files, if any。

这里的 target model 是单个明确模型或模型中的指定目标计算单元。例如：

* 一个指定的 Qwen block；
* 一个指定的 LLaMA-like block；
* 一个已有加速器项目中的目标 block。

这不是模型范围选择，而是单次设计目标。

---

### 4.2 给定可信模板库

Human 应提供或批准 trusted template library。

模板库可以包括：

* Linear / GEMM；
* RMSNorm / LayerNorm；
* RoPE；
* QK；
* Softmax 或 approximate softmax；
* AV；
* MLP；
* SwiGLU / GELU；
* residual add；
* FIFO；
* stream adapter；
* layout converter；
* DDR reader / writer；
* AXI wrapper；
* host runtime interface；
* stage-level testbench；
* top-level testbench；
* system-level testbench。

Agent 可以实例化、参数化、连接和小范围修复这些模板，但不能随意重写模板的核心语义。

这一点非常关键。SpatialAccAgent 的可信性不是来自 agent 自由写 RTL，而是来自：

**template-based generation under explicit design constraints**

即：

**在显式设计约束下，基于可信模板生成设计。**

---

### 4.3 批准初始架构计划

Agent 可以提出 processing unit 划分、pipeline stage、stream edge、buffer、DDR/AXI 访问方式、runtime 数据流和验证计划。

但 high-level architecture plan 需要 human 批准。

Human 主要判断：

* 这个架构是否符合目标模型语义；
* 这个架构是否符合目标平台；
* 这个架构是否符合设计目标；
* 这个架构是否在可信模板库支持范围内；
* 是否允许 agent 继续生成具体 design files。

Human 不需要检查每根信号，也不需要手动写代码。

---

### 4.4 批准重大修改

在设计闭环过程中，agent 可能提出一些重大修改。这些修改会影响全局结构，因此必须 human 批准。

例如：

* 改变 pipeline stage；
* 改变 tile size；
* 改变 parallelism；
* 改变 memory layout；
* 改变 data packing；
* 改变 numeric policy；
* 大规模修改模板；
* 为了 timing 加入新的 pipeline stage；
* 改变 AXI/DDR 访问方式；
* 改变主要 buffer 结构。

这些修改不是简单 bug fix，而是 design decision。Agent 可以分析和建议，但不能直接执行。

---

### 4.5 最终 sign-off

Human 负责最终确认：

* 设计是否通过所有必须的验证；
* 是否可以进入综合；
* 是否可以进入上板；
* 是否接受最终 benchmark report；
* 是否接受最终生成的 design package。

Human 不负责底层运行和调试，但负责最终 sign-off。

---

## 5. Agent 的职责

Agent 是 SpatialAccAgent 的执行主体。它负责在 human 给定边界内完成设计闭环。

### 5.1 构建并维护显式设计状态

Agent 的第一项核心职责是构建和维护显式设计状态，即 Spatial Accelerator Constraint Graph, SACG。

SACG 用于记录当前设计中必须保持一致的跨层约束，包括：

* model constraints；
* shape constraints；
* numeric constraints；
* stream constraints；
* beat-count constraints；
* memory constraints；
* pipeline constraints；
* verification constraints；
* deployment constraints。

Agent 每次生成或修改 design files 时，都必须同步更新 SACG 或检查是否仍然满足 SACG。

---

### 5.2 生成架构和流水计划

Agent 根据目标模型、目标平台、数值策略和模板库生成初始设计计划，包括：

* processing unit 划分；
* pipeline stage；
* stream order；
* buffer / FIFO；
* DDR/AXI access plan；
* runtime data movement；
* verification plan。

该计划提交给 human 批准。批准后，agent 才继续生成具体文件。

---

### 5.3 生成和连接设计文件

Agent 自动生成或修改以下 design files：

* Chisel modules；
* RTL wrappers；
* top-level connections；
* stream interconnect；
* DDR/AXI wrapper；
* host runtime；
* testbench；
* trace dumper；
* DDR image builder；
* simulation scripts；
* synthesis scripts；
* benchmark scripts；
* report parser。

Agent 的主要价值在于把这些文件和 SACG 绑定起来，确保它们不是互相独立生成，而是由同一个显式设计状态约束。

---

### 5.4 调用工具并收集结果

Agent 自动调用工具完成：

* Chisel compilation；
* RTL simulation；
* stage-level verification；
* top-level verification；
* system-level verification；
* synthesis；
* implementation；
* board run；
* benchmark。

Agent 需要把工具输出转成结构化结果，例如：

* pass / fail；
* mismatch location；
* numeric mismatch；
* missing beat；
* extra beat；
* wrong address；
* stream order mismatch；
* FIFO stall；
* deadlock；
* timing violation；
* resource overflow；
* runtime failure。

这些结果会被绑定到 SACG 中，作为后续定位和修复的依据。

---

### 5.5 定位被破坏的约束

当设计失败时，agent 不能只报告“仿真失败”或“输出错误”。

Agent 必须进一步判断：

* 哪个 checker 失败；
* 失败发生在哪一层；
* 相关 design file 是哪个；
* 相关 SACG node 或 edge 是哪个；
* 哪类 constraint 被破坏；
* 可能 root cause 是什么；
* 应该修哪一层。

例如：

| Failure symptom              | Violated constraint            |
| ---------------------------- | ------------------------------ |
| output 少一拍                   | beat-count constraint          |
| system-level output garbage  | memory constraint              |
| W4 output systematic bias    | numeric / memory constraint    |
| top-level attention mismatch | model / stream constraint      |
| FIFO 长时间 full 或 empty        | pipeline / liveness constraint |
| timing fix 后输出错              | pipeline / stream constraint   |

这一步是 SpatialAccAgent 区别于普通 coding agent 的核心。

---

### 5.6 执行受限修复

Agent 可以在允许范围内自动执行小修复，例如：

* 修正连接错误；
* 修正参数同步；
* 修正 loop bound；
* 修正 valid delay；
* 修正 address offset；
* 修正 script path；
* 重新生成 DDR image；
* 同步 runtime config；
* 小范围调整 FIFO depth；
* 重新运行 regression。

每次修复都必须记录：

* symptom；
* evidence；
* violated constraint；
* patch；
* expected effect；
* regression result。

Agent 不能只修改代码而不记录原因。

---

## 6. Checker / Tool 的职责

Checker 和真实工具结果负责判断 agent 的动作是否有效。

### 6.1 Checker 的目标

Checker 的目标不是替代所有仿真，而是将 design files、trace、logs 和 SACG 连接起来，让错误可以被准确发现和定位。

Checker 需要回答：

* 当前设计是否满足 SACG？
* design files 之间是否一致？
* trace 和预期 stream order 是否一致？
* beat count 是否正确？
* DDR image 和 RTL address trace 是否一致？
* numeric result 是否正确？
* pipeline 是否可能 deadlock？
* 修复后 regression 是否全部通过？

---

### 6.2 主要 checker

SpatialAccAgent 至少需要以下 checker：

1. **sacc-lint**
   检查 SACG 中 node、edge、constraint、file reference 是否完整。

2. **shape-check**
   检查 hidden size、head、head dim、tile、lane、beat 等参数是否一致。

3. **numeric-check**
   检查 scale、zero-point、rounding、saturation、bias、output 是否满足数值要求。

4. **stream-trace-check**
   检查 producer 和 consumer 的 stream order 是否一致。

5. **beat-count-check**
   检查 valid-ready transaction 数量是否正确，是否 missing beat 或 extra beat。

6. **addr-map-check**
   检查 DDR image、runtime buffer map 和 RTL address trace 是否一致。

7. **deadlock-check**
   检查 FIFO occupancy、valid-ready stall 和 bounded progress。

8. **regression-check**
   检查修复是否破坏已有通过的测试。

9. **report-check**
   检查 synthesis、timing、resource、board run 和 benchmark report 是否完整。

---

### 6.3 Checker 和 agent 的关系

Agent 可以提出修复建议，但 checker 决定是否通过。

Agent 可以解释 root cause，但 checker 和工具结果必须支持这个解释。

Agent 可以生成 patch，但 regression 通过之前，该 patch 不能被视为成功。

因此，框架的基本规则是：

**No checker pass, no design pass.**

中文：

**checker 不通过，设计就不能算通过。**

---

## 7. Agent 修复权限

为了避免 agent 无约束修改设计，SpatialAccAgent 将 repair 分为三类。

---

### 7.1 Agent 可以自动执行的修改

这类修改是局部的、可回归验证的，不改变主要设计语义。

Agent 可以自动执行：

* 重新生成 design files；
* 修正 signal connection；
* 修正参数同步；
* 修正 script；
* 修正 trace parser；
* 修正 wrapper / runtime 中的字段同步；
* 修正明显的 valid delay；
* 修正明显的 address offset；
* 重新生成 DDR image；
* 小范围 FIFO depth 调整；
* 重新运行 regression。

条件是：

* 修改必须绑定到 violated constraint；
* 修改必须记录 repair log；
* 修改后必须重新运行 checker 和 regression。

---

### 7.2 需要 human 批准的修改

这类修改会影响全局架构、数据流或数值策略。Agent 可以提出建议，但不能直接执行。

需要 human 批准的修改包括：

* 改变 pipeline stage；
* 改变 tile size；
* 改变 parallelism；
* 改变 memory layout；
* 改变 data packing；
* 改变 numeric policy；
* 大规模修改 trusted template；
* 为了 timing 加入新的 pipeline stage；
* 改变 AXI/DDR 访问方式；
* 改变主要 buffer 结构；
* 改变整体 architecture plan。

这些修改必须由 human sign-off 后才能执行。

---

### 7.3 Agent 禁止执行的修改

Agent 永远不能执行以下行为：

* 删除 failing test；
* 修改 golden output 来让测试通过；
* 随意放宽 numeric tolerance；
* 改变模型语义；
* 把 GQA 当作 MHA 处理；
* 绕过 checker；
* 将 failed regression 标记为 pass；
* 在没有证据时声称 root cause 已确认；
* 为了通过测试隐藏错误；
* 在没有 human 批准时大规模重写 trusted template；
* 在没有 system-level regression 通过前进入 board benchmark；
* 用自然语言解释替代可执行 evidence。

这些是框架的 safety rules。

---

## 8. 单次运行的最小输入

SpatialAccAgent 单次运行的输入应保持简洁。

一个最小 Design Task Card 可以是：

```yaml
task_name: qwen_block_accelerator

target_model:
  name: Qwen2.5-0.5B
  source: /path/to/model_or_config

target_platform:
  name: target_fpga_board
  config: /path/to/platform_config

numeric_policy:
  name: W4A8
  config: /path/to/numeric_config

template_library:
  path: /path/to/templates

design_goal:
  primary: throughput
  secondary: resource

toolchain:
  simulation: verilator_or_chiseltest
  synthesis: vivado_or_vitis
```

该输入不包括：

* 模型范围；
* 是否支持完整模型；
* 论文 claim；
* 人工定义的功能正确性标准。

功能正确是默认前提，由 golden data、checker 和 regression 保证。

如果存在量化或近似计算，允许误差应来自 numeric policy，而不是 agent 临时决定。

---

## 9. 单次运行流程

SpatialAccAgent 的单次运行流程可以分为九步。

### Step 1：读取任务

Human 提供 Design Task Card。Agent 读取目标模型、目标平台、数值策略、模板库和设计目标。

---

### Step 2：建立初始 SACG

Agent 抽取并建立初始 SACG，包括 model、shape、numeric、stream、memory、pipeline、verification、deployment constraints。

Checker 运行 sacc-lint 和基础一致性检查。

---

### Step 3：生成初始架构计划

Agent 生成 processing unit、pipeline、stream、buffer、DDR/AXI 和 runtime 计划。

Human 审核并批准 major architecture plan。

---

### Step 4：生成设计文件

Agent 基于可信模板生成 Chisel、RTL wrapper、top-level connection、testbench、DDR image builder、runtime 和 scripts。

---

### Step 5：运行 stage-level verification

Agent 运行每个 processing unit 的测试，并收集结果。

Checker 检查 shape、numeric 和局部输出。

---

### Step 6：运行 top-level verification

Agent 运行 top-level simulation。

Checker 检查 stream order、beat count、valid-ready behavior、residual path 和 stage 之间的连接。

---

### Step 7：运行 system-level verification

Agent 接入 DDR image、AXI wrapper 和 runtime。

Checker 检查 address map、memory layout、runtime buffer map 和 RTL address trace 是否一致。

---

### Step 8：运行 backend closure

Agent 运行 synthesis、implementation、timing/resource report。

如果出现 timing 或 resource 问题，agent 先判断这是 backend issue、script issue、resource issue，还是需要 architecture-level change。

重大结构修改需要 human 批准。

---

### Step 9：运行 final regression 和 benchmark

Agent 重新运行所有必须的 regression，并生成 final report。

Human 进行最终 sign-off。

---

## 10. 从已有 Codex 设计过程提炼框架

你当前已经有一份从零开始通过 Codex 实现 accelerator、仿真、验证、上板的详细上下文文档。该文档应作为 SpatialAccAgent 的第一批真实设计记录。

第一步不是直接开发完整 agent，而是先把已有过程结构化成 Design Closure Trace。

每条 trace record 建议包含：

```text
step_id:
human_goal:
agent_action:
generated_file:
tool_command:
tool_result:
failure_symptom:
evidence:
root_cause:
violated_constraint:
repair_patch:
regression_result:
human_decision:
```

这些 trace 可以用于：

* 提炼 SACG schema；
* 建立 failure taxonomy；
* 生成 repair records；
* 设计 checker；
* 构造 motivating study；
* 作为论文中的真实 case evidence。

## 11. 开发路线

### Phase 1：Design Closure Trace

从已有 Codex 上下文文档中提取 30 到 100 条真实 design-step records。

重点提取：

* design action；
* generated files；
* tool logs；
* failure symptoms；
* root causes；
* repair patches；
* regression results。

---

### Phase 2：SACG v0

定义最小 SACG schema，覆盖：

* node；
* edge；
* constraint；
* design file；
* tool result；
* repair record。

第一版不追求完整，只要能描述已有真实 bug 和设计流程即可。

---

### Phase 3：Checker v0

优先实现最能体现 cross-layer consistency 的 checker：

* sacc-lint；
* shape-check；
* stream-trace-check；
* beat-count-check；
* addr-map-check；
* numeric-check。

---

### Phase 4：历史 bug 回放

将已有工程过程中的真实 bug 绑定到 SACG，检查：

* checker 是否能提前发现；
* agent 是否能定位 violated constraint；
* 修复是否可以更小；
* regression 是否更稳定。

这一步可以形成第一组 preliminary result。

---

### Phase 5：Agent 闭环接入

让 agent 根据 SACG 自动完成：

* design file generation；
* checker invocation；
* evidence classification；
* repair proposal；
* small repair execution；
* regression rerun；
* SACG update。

---

### Phase 6：Fault injection 和 ablation

主动注入典型错误，例如：

* GQA mapping bug；
* stream order bug；
* missing beat；
* wrong address；
* scale stride mismatch；
* FIFO deadlock；
* timing repair misalignment。

比较：

* 普通 agent；
* template-only flow；
* stage-local verification；
* full SpatialAccAgent。

证明 SACG 和 checker 能减少 bug escape、repair iterations 和 human debug effort。

---

## 12. 推荐论文描述

论文中可以这样描述人机分工：

**SpatialAccAgent does not make the agent an unconstrained hardware designer. In each run, the human designer provides one target model, the target platform, the numeric policy, the trusted template library, and the design goal. The agent maintains the cross-layer constraint state, generates and connects design files, runs verification and backend tools, classifies tool results, locates broken constraints, and performs limited repairs. Human input is reserved for major design changes and final sign-off. Each agent action must be checked by executable checkers or real tool results before it is accepted.**

## 13. 最终框架边界

SpatialAccAgent 的最终框架边界可以总结为：

**Input:**
one target model, one target platform, one numeric policy, one trusted template library, one design goal.

**Agent responsibility:**
maintain design state, generate files, connect modules, run tools, collect results, find broken constraints, repair local issues, rerun tests.

**Human responsibility:**
define the task, provide trusted templates, approve major design changes, and sign off final results.

**Checker responsibility:**
verify whether the design files, traces, memory layout, runtime config, and backend results are consistent with the design state.

**Core rule:**
agent suggestions are not enough; every accepted design change must be supported by checker pass or real tool result.

---

## 14. 最终一句话总结

**SpatialAccAgent 的人机分工不是“human 提需求，agent 随便设计”，而是“human 给定单个目标设计和可信边界，agent 在显式约束状态下生成、连接、验证和修复设计文件，checker 和真实工具结果决定每一步是否有效”。**

这个边界既保留了 agent 的自动化价值，也避免了全自动硬件设计的不可信问题。
