我理解了。你要做的不是一个“debug agent”，也不是让 LLM 自由生成 RTL，而是一个**完整的、template-based spatial accelerator design agent framework**。

更准确地说，SpatialAccAgent 的完整定位应该是：

> **给定一个目标 LLM block、一个 FPGA 平台、一个数值策略和一个可信 Chisel 模板库，agent 不是自由写硬件，而是在模板库约束下完成 spatial accelerator 的规划、模板绑定、参数生成、Chisel 组合、验证数据生成、stage/top/system 验证、错误定位、受限修复和最终 design closure。**

这就和论文问题紧扣起来了：**Cross-Layer Consistency Problem** 不是只发生在 debug 阶段，而是从最早的 model spec → template selection → pipeline planning → Chisel generation 就已经开始了。后面的验证和修复只是暴露这些一致性问题的地方。

# 1. 框架核心定位要改成：Template-Constrained Agentic Design Closure

我建议框架的核心表述改成：

> **SpatialAccAgent is a template-constrained, state-guided, checker-verified agent framework for LLM spatial accelerator design.**

中文是：

> **SpatialAccAgent 是一个基于可信模板、由显式状态引导、由 checker 验证的 LLM spatial accelerator 设计 agent 框架。**

这里有三个关键词：

1. **template-constrained**：agent 不自由写硬件，而是基于 Chisel 模板生成和组合；
2. **state-guided**：所有生成动作都必须更新 SACG；
3. **checker-verified**：所有设计结果必须被 stage/top/system/backend checker 验证。

这比“LLM 生成 RTL”稳得多，也更符合 GPT4AIGChip 这类工作的经验：LLM 处理长代码和长依赖有困难，因此需要 modular and decoupled hardware template，而不是让模型一次性自由生成完整加速器。

# 2. 完整框架不是一个 debug loop，而是 10 个阶段

你前面指出得对：上下文文档主要记录了后半段验证和修复，但论文框架必须补全前半段。完整流程应是：

4. Spatial pipeline planning

这 10 个阶段共同解决一个问题：

当前上下文文档已经很好地支撑了后半段：它记录了真实 RTL 主链、11 个真实阶段数据、token window 验证策略、stage-level 逐级验证、Top 集成验证和 SystemTop/MIG 起步。 但完整框架还必须把“这些 stage 是如何由模板生成并组合起来的”补进去。

# 3. SpatialAccAgent 的完整架构应由 6 个核心模块组成

## 3.1 Design Task Manager：任务定义模块

输入不是一句自然语言，而是一个稳定的 task card。

最小内容：

```yaml
task_name: opt125m_fpga_accelerator
target_model:
  name: OPT-125M
  config_path: ...
target_platform:
  board: xcvu9p
numeric_policy:
  activation: int8/fp32 mixed
  weight: int8
  softmax: fp32/fixed-point
template_library:
  path: chisel_templates/
design_goal:
  primary: functional_closure
  secondary: resource/timing
toolchain:
  chisel: sbt
  simulation: verilator
  synthesis: vivado
```

这个模块的作用是防止 agent 从一开始就目标漂移。
它明确告诉 agent：

* 目标模型是什么；
* 用什么平台；
* 用什么数值策略；
* 只能用哪些模板；
* 当前目标是功能闭环、性能优化，还是上板验证。

---

## 3.2 Model-to-SACG Extractor：模型约束抽取模块

这个模块从模型配置和目标 block 中抽取设计约束。

它不是生成硬件，而是生成初始 SACG。

需要抽取：

* hidden size；
* FFN size；
* head number；
* head dim；
* MHA / GQA / MQA；
* LayerNorm / RMSNorm；
* RoPE 是否存在；
* activation function；
* residual path；
* Q/K/V shape；
* attention score shape；
* KV-cache shape；
* quantization scale；
* bias 语义；
* output dtype。

例如当前上下文中，真实主线是：

```text
FP32 input
-> LayerNormQ
-> QKVLinear
-> DM1FP32
-> SoftmaxPipFP32
-> DM2Quant
-> OutLinearFP32
-> ResAddFP32
-> LayerNormQ
-> FFNUp
-> FFNDownFP32
-> ResAdd2FP32
-> FP32 output
```

这个 pipeline 本身就应该成为 SACG 的 model/pipeline nodes。

这一阶段的输出不是 Chisel，而是：

```text
SACG-v0:
  model nodes
  operator nodes
  shape constraints
  numeric constraints
  residual constraints
  attention constraints
```

---

## 3.3 Template Library Manager：可信模板库管理模块

这是你刚才强调的关键点。

SpatialAccAgent 必须基于一个 Chisel template library，而不是让 LLM 自由发挥。

模板库至少包括：

```text
LayerNormQ template
QKVLinear template
DM1 / QK template
Softmax template
DM2 / PV template
OutLinear template
ResAdd template
FFNUp template
FFNDown template
Buffer / FIFO template
LoadUnit template
LoadWeight template
StoreUnit template
AXI / DDR / SystemTop template
Verilator harness template
```

每个模板不能只是代码文件，还必须有一个 **Template Spec**。不要叫 contract，可以叫 template spec。

每个 template spec 至少写清楚：

```yaml
template_name: QKVLinear
supported_op: qkv_projection
parameters:
  hidden_size:
  head_num:
  row:
  col:
  data_width:
io:
  input_shape:
  output_shape:
  stream_order:
  valid_ready:
numeric:
  weight_dtype:
  bias_dtype:
  scale_rule:
memory:
  weight_layout:
  bias_layout:
  buffer_banks:
timing:
  latency:
  ii:
  start_signal:
  done_signal:
allowed_agent_edits:
  - parameter binding
  - top connection
  - wrapper generation
forbidden_agent_edits:
  - change core compute semantics without approval
required_tests:
  - validate-stage qkv_proj
  - validate-top attention path
```

这个 template spec 是防止 Cross-Layer Consistency 断裂的关键。

因为 agent 生成每个 stage 时，不能只看 Chisel 代码，还必须知道：

* 这个模板要求什么输入顺序；
* 输出 beat 是什么顺序；
* valid/last 怎么打；
* scale 怎么解释；
* bias 是 int8 还是 fp32；
* weight packing 怎么排；
* top-level 如何连接。

你的上下文里大量 bug 都说明了这一点。例如 QKV 后来不是简单修改一个 RTL，而是重新确认真实公式 `round(acc * weight_scale + bias_int8 * bias_scale)`，并同步修改 RTL 接口、Top、SystemTop、testbench 和窗口生成脚本。 这就是 template spec 必须记录的跨层数值约束。

---

## 3.4 Pipeline Planner：空间流水规划模块

这个模块负责把 model graph 映射成 spatial pipeline。

它要做的不是自由设计，而是从模板库中选择 stage 并连接。

输入：

* SACG-v0；
* template library；
* platform profile；
* numeric policy。

输出：

```text
pipeline plan:
  S1: LayerNormQ
  S2: QKVLinear
  S3: DM1FP32
  S4: SoftmaxPipFP32
  S5: DM2Quant
  S6: OutLinearFP32
  S7: ResAddFP32
  S8: LayerNormQ
  S9: FFNUp
  S10: FFNDownFP32
  S11: ResAdd2FP32
```

同时还要生成：

* stage order；
* stream edges；
* residual edges；
* memory edges；
* initialization order；
* runtime config order；
* verification order。

这一步要特别注意：

> **pipeline plan 不是画图，而是约束集合。**

例如：

* QKV 的输出顺序必须和 DM1 / VCache / DM2 的输入顺序一致；
* Softmax 的 mask 语义必须和 DM1 输出地址一致；
* OutLinear 的输入必须和 DM2 输出 head/token 顺序一致；
* ResAdd1 的 residual 输入必须和 OutLinear 输出 beat 对齐。

上下文里 Top 集成问题几乎都来自这些边：Softmax 的 `layer_st` 时序、DM2 的 ctx scale、OutLinear 到 ResAdd1 的数据消费、QKV 的 1 LSB 偏差传播，都不是单个模块局部问题，而是 stage 之间的语义和时序边界问题。

---

## 3.5 Artifact Generator：模板绑定与代码生成模块

这个模块才是真正生成 Chisel / wrapper / testbench 的地方。

但它的能力边界要清楚：

Agent 可以做：

* 选择模板；
* 填参数；
* 生成 stage module instance；
* 生成 top-level connection；
* 生成 config wires；
* 生成 Verilator harness；
* 生成 data window script；
* 生成 SystemTop wrapper；
* 生成 Vivado scripts。

Agent 不应该自由做：

* 重写核心算法；
* 改变模型语义；
* 改变 quantization rule；
* 改变 stream order；
* 改变 memory layout；
* 改变 pipeline stage；
* 绕过已有 checker。

如果必须改，则需要 human approval。

这一阶段的输出包括：

```text
Chisel modules
Top.scala
Attention.scala
SystemTop / BoardTop
Verilator harness
data builder scripts
stage manifest
top window config
DDR image builder
Vivado scripts
```

每生成一个 artifact，必须同步更新 SACG。

这点非常重要。否则 agent 生成了代码，但 SACG 不知道代码已经改变，后续就无法判断一致性是否还成立。

---

## 3.6 Checker and Closure Engine：验证与闭环模块

这部分就是上下文文档中已经非常强的后半段。

它包括：

1. stage-level verification；
2. top-level verification；
3. system-level verification；
4. backend verification；
5. boundary localization；
6. bounded repair；
7. regression gate。

上下文中真实验证策略是从 `N=912` 大样本中切 token range，先做逐级验证，而不是直接把整条 Top 全链路一次性灌进去；这正是 Verification Ladder 的雏形。

这个模块要形成固定规则：

```text
stage pass != top pass
top pass != system pass
system pass != board pass
tolerance pass != exact pass
probe result != final evidence unless cross-checked
```

# 4. 整体 agent 角色划分

为了完整，但不要过度复杂，我建议第一版设计成 **one controller + five specialist agents**。

## 4.1 Controller Agent

负责全局调度。

它维护：

* current SACG；
* current task state；
* pass matrix；
* failed boundary；
* approved changes；
* rejected branches；
* next action。

它不直接写代码，而是调用下面几个 specialist agents。

---

## 4.2 Model and Constraint Agent

负责读取模型配置和模板需求，建立初始 SACG。

输出：

* model constraints；
* shape constraints；
* numeric constraints；
* required stages；
* required templates。

---

## 4.3 Template Binding Agent

负责从 template library 中选择模板并绑定参数。

输出：

* selected templates；
* template parameters；
* required code files；
* required top connections；
* required verification plan。

这个 agent 的核心约束是：

> **不能脱离模板自由写硬件。**

---

## 4.4 Integration Agent

负责把各 stage 连接成 Top / Attention / SystemTop。

它重点维护：

* stream order；
* valid/ready；
* last/st；
* beat count；
* buffer；
* residual path；
* memory layout；
* init order；
* runtime config。

这正是 Cross-Layer Consistency 最容易出问题的地方。

---

## 4.5 Verification Agent

负责生成真实数据窗口、运行 Verilator、解析 log、生成 pass/fail report。

它调用：

```text
prepare-stage-window
validate-stage
prepare-top-window
validate-top
prepare-system-window
validate-system-top
synthesis / timing report
```

---

## 4.6 Debug and Repair Agent

负责失败定位和受限修复。

它不能直接乱改。

它必须输出：

```text
symptom
evidence
first failing boundary
broken constraint
proposed minimal fix
files to modify
regression plan
approval needed or not
```

如果没有证据，不能修。

如果连续两次修复无效，必须回到 Boundary Locator，而不是继续 patch。

# 5. 完整流程应该这样写

下面是我认为最完整、最贴合论文的流程。

## Stage 0：Task Card 输入

Human 给定：

* target model；
* target platform；
* numeric policy；
* template library；
* design goal；
* toolchain。

输出：

* design task card。

---

## Stage 1：Model Constraint Extraction

Agent 读取模型结构，生成初始 SACG。

输出：

* operator list；
* shape constraints；
* numeric constraints；
* attention constraints；
* residual constraints。

检查：

* model config 是否完整；
* hidden/head/FFN/seq 参数是否明确；
* numeric policy 是否明确。

---

## Stage 2：Template Selection

Agent 从 Chisel template library 中选择 stage templates。

输出：

* selected templates；
* template coverage report；
* missing template list。

检查：

* 每个 model op 是否有模板覆盖；
* 模板是否支持当前 shape；
* 模板是否支持当前 numeric policy；
* 模板是否支持目标平台资源限制。

如果缺模板，则进入 human approval。

---

## Stage 3：Pipeline Planning

Agent 生成 spatial pipeline plan。

输出：

* stage order；
* stream edges；
* residual edges；
* memory edges；
* init order；
* verification order。

检查：

* stage input/output shape；
* stream beat order；
* residual path alignment；
* buffer depth；
* top-level timing assumption。

---

## Stage 4：Template Parameter Binding

Agent 绑定每个 template 的参数。

输出：

* Chisel parameter files；
* template config files；
* SACG updated constraints。

检查：

* ROW/COL/lane/data width；
* weight layout；
* bias layout；
* scale rule；
* buffer bank；
* latency；
* valid/last behavior。

---

## Stage 5：Module Generation

Agent 生成或实例化 Chisel modules。

注意：这里不是自由生成 RTL，而是：

```text
template + parameters + small glue code
```

输出：

* stage modules；
* local wrappers；
* parameter files。

检查：

* Chisel compile；
* module IO；
* local lint；
* template spec compliance。

---

## Stage 6：Top Integration

Agent 连接所有 stage。

输出：

* Top.scala；
* Attention.scala；
* stream adapters；
* FIFOs；
* residual buffers；
* config wires。

检查：

* stream order；
* beat count；
* valid alignment；
* start/done signal；
* memory init sequence；
* residual bypass。

---

## Stage 7：Verification Artifact Generation

Agent 生成真实验证数据。

输出：

* stage windows；
* top windows；
* golden outputs；
* weight/bias/scale artifacts；
* DDR image；
* runtime config；
* compare scripts。

检查：

* shape；
* dtype；
* packing；
* scale；
* bias；
* token_start/token_count；
* head selection；
* exact vs tolerance rule。

上下文里真实 dump 标签复杂、shape/tensor label 不一致、scale 语义复杂，这说明这个阶段必须是框架核心，而不是附属脚本。

---

## Stage 8：Stage-Level Verification

Agent 逐级运行每个 stage。

输出：

* stage pass matrix；
* failed stage report；
* first mismatch；
* waveform/probe if needed。

检查：

* numeric correctness；
* output beat count；
* last signal；
* stage-local memory layout。

---

## Stage 9：Top-Level Verification

Agent 运行完整 Top。

输出：

* top pass/fail；
* first failing boundary；
* staged compare points；
* propagated error chain。

检查：

* stage-to-stage consistency；
* stream handoff；
* valid/ready；
* residual alignment；
* top input/output order。

这就是上下文中最重要的真实过程：很多 stage 已经 pass，但 top 中仍然出现 Softmax、DM2、OutLinear、ResAdd1、QKV 数值语义等跨层问题。

---

## Stage 10：System / Backend Closure

Agent 生成 SystemTop / BoardTop 并运行 system-level 验证。

输出：

* SystemTop；
* DDR image；
* MIG-like simulation；
* synthesis report；
* timing/resource report；
* board run report。

检查：

* DDR layout；
* address map；
* preload order；
* runtime config；
* timing；
* resource；
* board I/O。

上下文中已经明确当前 `Top.scala` 应作为 compute core，真正上板需要外层 `SystemTop / BoardTop` 负责 DDR/MIG、数据搬运和结果接收。 这正好对应框架最后一层。

# 6. 这个完整框架如何紧扣论文问题？

你的论文问题是 Cross-Layer Consistency，所以框架每一阶段都必须围绕这个问题展开。

| 阶段                               | 可能破坏的一致性                         |
| -------------------------------- | -------------------------------- |
| Model extraction                 | model semantics / shape          |
| Template selection               | op-template match                |
| Pipeline planning                | stream / residual / memory       |
| Parameter binding                | numeric / layout / latency       |
| Module generation                | IO / valid / local behavior      |
| Top integration                  | beat / start / done / ordering   |
| Verification artifact generation | data/golden/scale/bias semantics |
| Stage verification               | local correctness                |
| Top verification                 | global composition               |
| System verification              | DDR/runtime/harness              |
| Backend closure                  | timing/resource vs function      |

所以 SpatialAccAgent 的核心 claim 不是：

> 我们可以让 agent 生成 Chisel。

而是：

> 我们让 agent 在 template-based spatial accelerator design 的每一步都维护跨层约束，并通过 checker 防止 artifact 组合后失去一致性。

# 8. 最终框架一句话

我建议把完整框架压成这一句话：

> **SpatialAccAgent starts from a target LLM block and a trusted Chisel template library. It extracts model and numeric constraints, selects and binds pipeline-stage templates, generates Chisel and verification artifacts, connects stages into a spatial pipeline, and then uses stage/top/system checkers to detect, locate, and repair cross-layer consistency violations until the accelerator design reaches closure.**

中文：

> **SpatialAccAgent 从目标 LLM block 和可信 Chisel 模板库出发，抽取模型与数值约束，选择并绑定 pipeline stage 模板，生成 Chisel 和验证 artifact，将各 stage 连接成 spatial pipeline，并通过 stage/top/system checker 发现、定位和修复跨层一致性错误，直到加速器设计闭环。**

这才是完整的 agent 框架。
