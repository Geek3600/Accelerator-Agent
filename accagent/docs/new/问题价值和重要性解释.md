你的理解基本正确，但我建议把“最终设计出来的加速器可能不是很好”改得更强一些：

> **不是“可能不是很好”，而是可能出现局部正确、全局错误；局部可跑、系统不可部署；局部优化、全局 QoR 退化；局部修复、引入新 bug。**

这才是问题的严重性。

所以我们要向审稿人证明的不是：

> 我们发现了一个听起来合理的问题。

而是证明：

> **这个问题真实存在、代价很高、已有工作只解决了局部、并且我们的方法能定量降低这个问题带来的失败和调试成本。**

# 1. 审稿人真正会问什么？

DAC 审稿人不会只问“这个问题有没有道理”。他们会问四个问题：

1. **Existence：这个问题真的存在吗？**
2. **Severity：这个问题严重到值得一篇 DAC 论文吗？**
3. **Generality：这是不是你们某一个项目里的偶然 bug？**
4. **Solvability：你们的方法是否真的比普通 agent / compiler / template flow 更好？**

所以我们论文要围绕这四点构造证据链。

---

# 2. 我们的问题价值要从三个方向证明

## 2.1 前人工作已经独立暴露了这个问题的“碎片”

这一点非常关键。我们不能让审稿人觉得 cross-layer consistency 是我们自己发明出来的概念。要证明：**前人工作虽然没有这样命名，但它们已经反复遇到这个问题。**

### StreamTensor 暴露了 dataflow 层面的跨模块一致性问题

StreamTensor 明确指出，stream-based dataflow accelerator 的难点包括 inter-kernel correlation、external memory access、stream-based kernel fusion、FIFO sizing。尤其是 producer/consumer stream layout 不兼容会导致错误数据解释，FIFO sizing 不当会导致 stall cascade 和 deadlock。

这说明：即使不考虑 LLM agent，**spatial/dataflow accelerator 本身就存在跨 kernel、stream、memory、FIFO 的一致性问题**。

但 StreamTensor 的解决范围主要在 compiler IR 内部，例如 itensor、kernel fusion、FIFO sizing、runtime codegen。它证明这个问题重要，但没有解决 agent 从文档、模板、Chisel/RTL、trace、DDR image、backend report 到 repair log 的全链路设计状态维护问题。

---

### Allo 暴露了 multi-kernel composition 的一致性问题

Allo 的动机之一就是从 single-kernel optimization 扩展到 complex multi-kernel accelerator design。它指出现实设计中多个 kernel 的 interface 和 optimization 可能不兼容；简单级联优化 kernel 不保证得到高质量设计。Allo 通过 composable schedules、type-safe composition、hierarchical dataflow graph 来解决一部分 kernel composition 问题。

这说明：**局部优化的 kernel 并不能自动组成全局正确、高质量的 accelerator。**

这和我们的论点高度一致，只是 Allo 解决的是 ADL/compiler 里的 composition，而我们解决的是 agentic design closure 中跨 model、pipeline、RTL、memory、runtime、verification、backend 的一致性维护。

---

### GPT4AIGChip 暴露了 LLM 在硬件设计中会丢失跨模块依赖

GPT4AIGChip 已经观察到 LLM 在 accelerator design 中常见失败包括 variable misinterpretation、inability to capture long dependencies、overlooking crucial instructions、over-simplified implementation。它的结论是需要 decoupled hardware template 和分解任务，避免 LLM 一次性处理过长依赖。

这正好说明：**LLM agent 特别容易丢失跨阶段、跨模块约束。**

但是 GPT4AIGChip 的主要解决方案是 LLM-friendly template 和 demo-augmented prompt。它降低了 code generation 难度，却没有形成一个可检查的全局 design state。我们的价值就在这里：不只是把任务拆开，而是让拆开的任务仍然被同一个 Spatial Accelerator Constraint Graph 约束住。

---

### Design Conductor 暴露了 agentic chip design 的 closure 问题

Design Conductor 2.0 已经展示 agent 可以构建复杂 accelerator，VerTQ 包含 5,129 个 FP16/FP32 arithmetic units，并映射到 FPGA。 但它同时指出芯片设计流程包含 architecture、RTL/testbench、verification、synthesis、P&R、power、packaging 等多个步骤，成本巨大；而且 chip 不是软件，bug 不能靠后续 patch 修复，verification 因此更加关键。

更重要的是，Design Conductor 2.0 还明确提到 verification 和 timing closure 是最昂贵的部分，并观察到有时系统会把本可通过 backend script 修复的问题错误地转成复杂 RTL 修改。

这说明：**agentic chip design 现在真正昂贵的部分不是“会不会写代码”，而是如何在复杂反馈中判断该修哪一层。**

这就是我们的问题价值。

---

# 3. 论文里应该如何证明“这不是自嗨”？

我建议用一个四层证据结构。

---

## 第一层：Prior-work evidence

目的：证明问题不是你们凭空造出来的。

论文中可以这样写：

> Prior works have independently exposed different fragments of the same cross-layer consistency problem. Dataflow compilers observe stream layout mismatch, DMA coupling, and FIFO deadlock. ADLs observe that composing optimized kernels can introduce incompatible interfaces and suboptimal global designs. LLM-based accelerator generation observes that models lose long dependencies across hardware modules. Long-horizon chip agents observe that verification and timing closure dominate cost, and that distinguishing backend fixes from RTL fixes remains difficult. These symptoms point to a common missing abstraction: an explicit, executable design state that spans model semantics, spatial pipeline, hardware artifacts, memory/runtime layout, verification evidence, and backend feedback.

这段的作用是告诉审稿人：
**我们不是发明了一个空问题，而是把多个方向都遇到的碎片问题统一抽象出来。**

---

## 第二层：Motivating study

目的：证明这个问题在我们目标场景里真实存在，而且高频。

这部分非常重要。你们需要在论文 Motivation 里做一个小型实证研究，最好在方法之前出现。

### 设计方式

选 2–3 个 decoder-only LLM block：

* OPT/GPT-2 style；
* LLaMA style；
* Qwen style。

然后让几种 baseline flow 去生成/集成 accelerator：

1. **普通 multi-agent flow**：planner / coder / verifier，没有 SACG；
2. **template-only flow**：用模板生成，但没有全局 constraint graph；
3. **stage-local verification flow**：每个 PU 都测，但不做 top/system consistency check；
4. **你们的 full SpatialAccAgent**。

对前三个 baseline，记录自然出现的 bug，不需要一开始就做到完整可用。

### 要统计什么？

统计所有失败，并按 failure taxonomy 分类：

| Failure class        | 例子                                       | 证明什么                             |
| -------------------- | ---------------------------------------- | -------------------------------- |
| model/shape mismatch | GQA head mapping 错                       | 模型语义会跨层丢失                        |
| numeric mismatch     | W4 scale stride 错                        | 数值策略不是局部 GEMM 问题                 |
| stream mismatch      | producer/consumer tile order 不一致         | stage-level 正确不代表 top-level 正确   |
| beat-count bug       | output 少一拍                               | ready/valid 协议需要全局约束             |
| memory-layout bug    | DDR image 和 RTL address stride 不一致       | system-level artifact 必须和 RTL 绑定 |
| liveness bug         | FIFO depth 不足导致 deadlock                 | pipeline 局部正确不代表全局活性             |
| backend repair bug   | timing fix 加 register 破坏 valid alignment | 后端修复会反向影响流水语义                    |

### 最强指标

你们要给出这种表：

| Metric                           | No SACG | Template-only | Stage-local verification | Full SpatialAccAgent |
| -------------------------------- | ------: | ------------: | -----------------------: | -------------------: |
| total bugs                       |       高 |             中 |                        中 |                    低 |
| bugs escaping to system-level    |       高 |             高 |                        中 |                    低 |
| average localization iterations  |       高 |             高 |                        中 |                    低 |
| human interventions              |       高 |             中 |                        中 |                    低 |
| repair patch size                |       大 |             中 |                        中 |                    小 |
| regression failures after repair |       高 |             中 |                        中 |                    低 |
| design closure success           |       低 |             中 |                        中 |                    高 |

这张表比任何 narrative 都更有说服力。

---

## 第三层：Fault injection

目的：证明问题不是你们刚好遇到几个 bug，而是一类系统性 failure space。

你们可以主动注入错误：

* GQA KV-head mapping 错；
* RoPE dimension offset 错；
* W4 scale layout 错；
* stream tile order reversal；
* valid 少打一拍；
* FIFO depth 太小；
* residual bypass 接错；
* DDR base address offset 错；
* AXI burst length 错；
* runtime output window size 错；
* timing fix 多加一拍但没改 valid delay。

然后比较：

| Method                  | Detection rate | Localization accuracy | Repair success | Avg. iterations |
| ----------------------- | -------------: | --------------------: | -------------: | --------------: |
| log-only agent          |              低 |                     低 |              低 |               高 |
| tests-only agent        |              中 |                   低/中 |              中 |               高 |
| constraint checker only |    高 detection |        中 localization |       无 repair |               - |
| Full SpatialAccAgent    |              高 |                     高 |              高 |               低 |

这组实验会非常强，因为它证明：

> **cross-layer consistency 不是口号，而是可以通过故障空间系统测量的问题。**

---

## 第四层：Ablation

目的：证明 SACG 里的每一类 constraint 都有价值，不是堆概念。

你们可以逐个移除：

* no shape constraint；
* no numeric constraint；
* no stream constraint；
* no beat-count constraint；
* no memory constraint；
* no liveness constraint；
* no deployment/backend constraint；
* no evidence classifier；
* no repair-log protocol。

然后观察哪些错误逃逸。

例如：

| Removed component         | Expected failure                                |
| ------------------------- | ----------------------------------------------- |
| no shape/model constraint | GQA/RoPE/head mapping bugs 增加                   |
| no numeric constraint     | scale/rounding/saturation mismatch 难定位          |
| no stream constraint      | tile order、head order、lane order 错误逃逸           |
| no beat-count checker     | missing/extra beat 逃逸到 top-level                |
| no memory constraint      | DDR image/runtime/address bugs 逃逸到 system-level |
| no liveness checker       | FIFO deadlock 晚发现                               |
| no backend constraint     | timing repair 引入 pipeline semantic bug          |

这会证明你们的方法不是“把一堆 checker 拼起来”，而是每类 constraint 都对应真实失败模式。

---

# 4. 你们要把“问题价值”包装成一个更高层的趋势

这篇论文的价值不只是一个 LLM accelerator 工具，而是一个新的 EDA 研究趋势：

> **As LLM agents move from code generation to long-horizon hardware design, the bottleneck shifts from generating individual artifacts to maintaining a consistent design state across artifacts.**

中文：

> **当 LLM agent 从生成单个 RTL 模块走向长期复杂硬件设计时，瓶颈不再是生成某段代码，而是维护跨 artifact 的一致设计状态。**

这句话非常重要。它把你们的工作从“某个工具”提升到“agentic EDA 的下一阶段问题”。

前人工作可以形成一个演进链：

1. **SpecLLM / GPT4AIGChip / RTLSquad / VeriOpt**
   LLM 能生成 specification、HLS/RTL、优化 PPA、提供 decision path。

2. **ChatEDA / Design Conductor**
   LLM agent 能调用工具，甚至能跨 RTL-to-GDSII 或 concept-to-layout 长流程。

3. **Allo / StreamTensor**
   spatial/dataflow accelerator 需要结构化 IR、type system、stream layout、FIFO sizing、runtime generation。

4. **我们的观察**
   当这些能力汇合到 LLM spatial accelerator design 时，最缺的是一个跨 model、pipeline、RTL、memory、runtime、verification、backend 的显式 design state。

5. **我们的贡献**
   Spatial Accelerator Constraint Graph + constraint-guided agentic design closure。

这条演进链很自然。

---

# 5. 论文 Motivation 可以这样组织

我建议 Motivation 章节分三小节。

## 5.1 Local success does not imply global closure

用真实例子说明：

* QKV GEMM stage-level 正确；
* RoPE stage-level 正确；
* attention stage-level 正确；
* DDR image builder 也能生成文件；
* runtime 也能启动；
* 但 system-level output 错，因为 Qwen GQA 的 query-head 到 KV-head mapping 在 stream schedule 和 memory packing 中不一致。

结论：

> **Local verification is insufficient because the violated assumption spans model semantics, stream order, and memory layout.**

---

## 5.2 Existing agents lack an explicit design state

展示一个普通 agent 的失败：

* 看到 output mismatch；
* 先怀疑 softmax approximation；
* 改了 numeric tolerance；
* 又怀疑 quant scale；
* 最后才发现是 DDR offset 或 stream order；
* 修复 patch 很大，甚至破坏已有 regression。

结论：

> **Without explicit constraints, agent repair becomes symptom-driven rather than invariant-driven.**

---

## 5.3 Constraint-guided design state enables early detection and minimal repair

展示 SACG 后：

* checker 发现 producer/consumer stream order 不一致；
* 或 addr-map-check 发现 DDR layout 和 RTL trace 不一致；
* agent 直接定位 violated constraint；
* 修最小 patch；
* regression 通过。

结论：

> **Explicit constraints turn ambiguous tool evidence into actionable repair targets.**

---

# 6. 最核心的“价值证明”公式

你们可以把问题价值压成一个很清楚的逻辑：

> **如果一个问题满足：高频出现 + 高调试成本 + 会逃逸到后期 + 现有方法只局部覆盖 + 我们能显著降低逃逸和修复成本，那么这个问题就值得解决。**

对应你们的证据：

| 价值维度      | 你们需要给出的证据                                                      |
| --------- | -------------------------------------------------------------- |
| 高频出现      | motivating study 中 bug taxonomy 统计                             |
| 高调试成本     | localization iterations / wall-clock time / human intervention |
| 会逃逸到后期    | bug escape rate: stage → top → system → board                  |
| 现有方法只局部覆盖 | prior-work matrix                                              |
| 我们能解决     | ablation + fault injection + closure success                   |

这就是审稿人会认可的证据链。

# 7. 最建议你们在论文里打出的 claim

不要说：

> Cross-layer consistency is important because we think so.

要说：

> In our motivating study, most failures in agentic LLM accelerator design were not syntax errors or isolated module bugs. They were cross-layer consistency failures: stage-local artifacts passed their own checks, but violated assumptions shared with other stages, such as stream order, memory layout, numeric scale, or deployment configuration. These failures were costly because they often escaped to top/system-level verification and required multiple repair iterations. This motivates explicit constraint states for agentic design closure.

中文：

> 在我们的初步研究中，大多数失败不是语法错误或孤立模块错误，而是跨层一致性错误：单个 stage 可以通过局部检查，但它与其他 stage 共享的假设被破坏，例如 stream order、memory layout、numeric scale 或 runtime/deployment 配置。这类错误代价高，因为它们经常逃逸到 top/system-level 才暴露，并需要多轮修复。因此，agentic design closure 需要显式的 constraint state。

这就是最有说服力的问题价值表述。

# 8. 你们应该如何设计第一组 preliminary result

现在最该做的不是马上完整实现全系统，而是做一个 **Problem Importance Study**。

最小版本如下：

### 对象

* 一个 OPT/GPT-2 block；
* 一个 LLaMA/Qwen-like block；
* W8A8 或 W4A8；
* 当前已有 Chisel/RTL/template/trace。

### 操作

让 baseline agent 或人工-template flow 完成：

* module generation；
* top connection；
* trace verification；
* DDR image；
* system simulation。

### 记录

每次 failure 都记录：

```text
symptom:
evidence:
escaped_level:
root_cause:
violated_constraint:
repair_iterations:
manual_time:
patch_size:
regression_result:
```

### 目标数字

你们最终希望得到类似这样的结果：

* 60–80% 的非语法错误属于 cross-layer consistency failure；
* 其中 40–60% 不能在 stage-level 被发现；
* 无 SACG 时平均需要 3–5 轮 repair；
* 有 SACG/checker 后，定位轮数下降到 1–2；
* bug escape 到 system-level 的比例显著下降；
* human intervention 显著下降。

这些数字不用一开始就很漂亮，但必须真实、可解释、可复现。

# 9. 对你刚才理解的进一步修正

你刚才说：

> agent 只局限于本阶段内的目标，导致即使逐个阶段可以跑通，但是从全局来看，最终设计出来的加速器可能不是很好。

我建议改成：

> agent 在每个阶段都能生成看似正确的 artifact，但缺少一个显式的全局设计状态来维护跨阶段共享约束。因此，局部 artifact 可以分别通过检查，但它们组合后可能违反模型语义、数值策略、stream 协议、memory layout、runtime 配置或 backend 假设，导致系统级错误、QoR 退化、调试困难和修复不稳定。

这个表述更准、更硬、更像论文。

# 10. 最终回答：如何证明这个问题有价值？

一句话：

> **用“前人工作独立暴露问题碎片 + 我们自己的 motivating study 统计真实失败 + fault injection 证明失败空间普遍 + ablation 证明 SACG 能降低失败逃逸和修复成本”这四层证据证明。**

这四层一旦做出来，审稿人就很难说你们是在自嗨。因为你们不是只提出了一个概念，而是证明了：

1. 这个问题在已有研究中反复出现；
2. 这个问题在 LLM spatial accelerator agent 中真实、高频、代价高；
3. 这个问题不是个例，而是一类可系统注入和测量的 failure space；
4. 你们的方法可以定量降低 bug escape、repair iterations、human intervention，并提高 design closure success。

这才是 DAC 级问题定义的价值证明。
