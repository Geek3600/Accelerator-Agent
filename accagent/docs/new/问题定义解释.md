最核心一句话是：

> **我们论文解决的问题不是“LLM 能不能生成 RTL”，而是：当 LLM agent 参与 LLM spatial accelerator 设计时，如何在模型语义、空间流水、Chisel/RTL、stream 协议、DDR/AXI layout、runtime、验证 trace、综合/上板结果之间，持续保持跨层一致性，并在不一致时自动定位和修复。**

这个问题可以命名为：

> **Cross-Layer Consistency Problem in Agentic LLM Spatial Accelerator Design**
> 面向 agentic LLM spatial accelerator 设计的跨层一致性问题。

---

## 1. 先用一句人话解释

你可以把真实 accelerator 设计理解成一条链：

> 模型配置 → 算子语义 → 空间流水 → Chisel 模块 → RTL → stream trace → DDR image → AXI wrapper → host runtime → 仿真 → 综合 → 上板

每一层都不是孤立的。比如 Qwen 的 GQA 里，`num_heads=14`，`num_kv_heads=2`，这个信息最开始在模型配置里；之后会影响 Q/K/V projection shape、RoPE head layout、attention head mapping、KV-cache layout、stream 发送顺序、DDR packing、RTL address generator、runtime buffer offset。

**问题是：这些约束在传统设计流程里大多是隐式传播的。**

人类工程师靠经验记住它们；普通 agent 靠上下文猜它们；compiler 只在自己的 IR 范围内维护它们。

于是当系统出错时，agent 只看到：

> output mismatch
> simulation timeout
> missing beat
> wrong address
> timing violation
> numeric mismatch

但它不知道这个错误到底来自：

* 模型语义错了？
* shape 错了？
* stream order 错了？
* DDR packing 错了？
* quant scale 错了？
* valid-ready 少打一拍？
* runtime buffer map 错了？
* backend timing fix 改坏了流水？

**这就是我们定义的问题。**

---

## 2. 更精确的问题定义

我们的论文问题可以定义为：

> **Given a decoder-only LLM block specification, hardware platform constraints, accelerator templates, and tool feedback, how can an agentic design system explicitly maintain, check, and repair the cross-layer consistency constraints among model semantics, spatial pipeline structure, hardware implementation artifacts, memory/runtime layout, verification traces, and backend deployment evidence?**

中文就是：

> **给定 decoder-only LLM block、硬件平台、加速器模板和工具反馈，如何让 agent 系统显式维护、检查和修复模型语义、空间流水、硬件实现、内存布局、runtime、验证 trace 和后端部署证据之间的跨层一致性约束？**

这才是论文真正解决的问题。

---

## 3. 不是解决什么？

这一点必须讲清楚，否则很容易被前人工作打穿。

### 不是解决 “如何生成 Verilog/RTL”

因为 GPT4AIGChip、RTLSquad、Design Conductor 这类工作已经在探索 LLM 生成 HLS/RTL 或 agentic chip design。GPT4AIGChip 关注 LLM 如何根据自然语言生成 AI accelerator，并指出 LLM 容易出现变量误解、长依赖捕获失败、忽略关键指令、实现过度简化等问题；它的解决方向是 decoupled hardware template 和 demo-augmented prompt。

所以我们不能说：

> 我们第一次让 LLM 生成 accelerator。

我们要说：

> 生成 RTL 只是其中一个 artifact。我们解决的是这些 artifact 之间的跨层一致性维护和修复。

---

### 不是解决 “如何从 PyTorch 编译出 dataflow accelerator”

因为 StreamTensor 已经很强。它从 PyTorch/MLIR 出发，生成 stream-based dataflow accelerator，并且显式处理 kernel fusion、stream layout、FIFO sizing、DMA、runtime 等问题。 它甚至提出 itensor type 来编码 stream layout，解决 producer/consumer stream order 是否匹配的问题。

所以我们不能说：

> 现有方法不能生成 LLM dataflow accelerator。

我们要说：

> StreamTensor/Allo 解决的是结构化 IR 里的 compiler/dataflow optimization。我们解决的是 agentic design 里，从非结构化文档、模型配置、模板、代码、trace、DDR image、runtime、backend report 之间维护显式设计状态的问题。

---

### 不是解决 “如何组合多个 kernel”

因为 Allo 已经提出 composable schedules、decoupled hardware customization、hierarchical dataflow graph、type-safe composition，并且已经展示了 GPT2 FPGA accelerator。

所以我们不能说：

> 现有 ADL 不能做 spatial accelerator composition。

我们要说：

> Allo 解决的是 programmer/compiler 如何表达和组合 accelerator design；我们解决的是 agent 如何在整个设计闭环中维护跨层设计约束，并用工具证据驱动修复。

---

### 不是解决 “agent 能不能端到端做芯片”

因为 Design Conductor 2.0 已经展示了 agent 可以构建 VerTQ 这种复杂 accelerator，并完成 architecture、implementation、verification、timing optimization 和 FPGA mapping。 但它也暴露出 verification、floating-point numerics、timing closure、backend-vs-RTL fix 判断等问题仍然非常昂贵、复杂。

所以我们不能说：

> 现有 agent 不能做复杂 accelerator。

我们要说：

> Design Conductor 证明了 agentic chip design 可行，但它更像 impressive case study。我们要把其中最难的 design closure 问题形式化成可检查、可复现、可量化的 cross-layer consistency framework。

---

## 4. 我们到底发现了什么 gap？

我们发现的 gap 是：

> **现有方法缺少一个面向 agentic accelerator design 的显式跨层设计状态。**

更具体地说，现有方法通常有三类状态：

### 第一类：Compiler IR

比如 Allo/StreamTensor 的 IR。它们可以表示 tensor、layout、stream、kernel fusion、FIFO sizing。

但它们主要覆盖 compiler 内部的 structured representation。它们不一定覆盖：

* 模型文档里的语义假设；
* Chisel template 的参数绑定；
* RTL trace；
* DDR image；
* runtime buffer map；
* synthesis/P&R report；
* board log；
* repair history。

### 第二类：Natural-language agent context

比如 RTLSquad/Design Conductor 里的 agent discussion、decision path、tool log summary。

它可读，但不够可执行。它能解释 agent 为什么这样做，但很难机械地检查：

* 哪个 shape constraint 被破坏；
* 哪个 stream edge 少了 beat；
* 哪个 DDR region 和 RTL address generator 不一致；
* 哪次 repair 改动是否恢复了 invariant。

### 第三类：EDA tool reports

比如 simulation log、Vivado timing report、resource report、waveform。

它们是 evidence，但不是 design state。它们告诉你现象，不告诉你跨层根因。

所以我们的 gap 是：

> **Compiler IR 不够外延，natural-language context 不够可执行，EDA report 不够语义化。agentic accelerator design 缺少一个能贯穿模型、硬件、验证、部署和修复的显式设计状态。**

这个状态就是我们提出的 **Spatial Accelerator Constraint Graph, SACG**。

---

## 5. 为什么这个问题重要？

因为真实 bug 往往不是“代码写错一行”这么简单，而是跨层不一致。

比如：

### 例子 1：GQA mapping 错

模型配置里是：

> 14 query heads, 2 KV heads

RTL 里 Q/K/V GEMM 都可能分别正确，stage-level test 也可能通过。但 top-level attention 输出错，因为 query head 到 KV head 的 mapping 错了。

这不是单纯 RTL bug，而是：

> **model constraint 和 stream/memory constraint 不一致。**

---

### 例子 2：W4 scale stride 错

W4 weight 本身 packing 是对的，GEMM 模块也能跑。但 scale 的 layout 和 RTL 读取 stride 不一致，导致 output 有 systematic bias。

这不是单纯 quantization error，而是：

> **numeric constraint 和 memory-layout constraint 不一致。**

---

### 例子 3：输出少一拍

计算逻辑对，数值也对，但 valid-ready 协议里最后一个 beat 没发出来。

这不是模型语义 bug，而是：

> **beat-count constraint / stream protocol constraint 被破坏。**

---

### 例子 4：DDR 地址错

stage-level 和 top-level 都能过，因为输入直接喂 trace；system-level 上 DDR image 后输出 garbage。

这不是 datapath bug，而是：

> **memory constraint、runtime buffer map、RTL address generator 不一致。**

---

### 例子 5：timing repair 改坏流水

agent 为了修 timing 加了一拍 pipeline register，但没有同步调整 valid delay、residual bypass 或 output strobe。

这不是纯 timing 问题，而是：

> **backend repair 破坏了 pipeline/stream constraint。**

这些问题都说明：**真实 accelerator design closure 的核心不是“写代码”，而是“跨层一致性维护”。**

---

## 6. 用论文语言怎么定义？

你们可以把问题定义写成下面这个结构：

### 输入

* decoder-only LLM block specification；
* target FPGA/platform constraints；
* quantization/numeric policy；
* accelerator template library；
* toolchain feedback，包括 simulation、trace、synthesis、P&R、board log。

### 输出

* Chisel/RTL modules；
* top-level connections；
* stream interconnect；
* DDR/AXI wrapper；
* host runtime；
* verification scripts；
* packed weight/activation/DDR image；
* synthesis/deployment scripts；
* repair log；
* benchmark report。

### 目标

生成的 accelerator design package 必须满足：

* model semantics preserved；
* numeric behavior within tolerance；
* stream order and beat count correct；
* memory/runtime layout consistent；
* pipeline has bounded liveness；
* stage/top/system/board verification pass；
* implementation meets reasonable QoR。

### 核心挑战

这些性质横跨不同表示层，不能由单一 RTL checker、单一 compiler IR、单一 prompt 或单一 simulation log 完整维护。

### 我们解决

提出一个显式的 constraint state，也就是 SACG，让 agent 的每一步动作都围绕：

> update constraint → generate artifact → run checker → collect evidence → localize violated constraint → repair → regression

展开。

## 7. 最终一句话版本

你可以把论文的问题定义最终压成一句话：

> **This paper addresses the cross-layer consistency problem in agentic LLM spatial accelerator design: when LLM agents transform a decoder-only Transformer block into deployable FPGA artifacts, the implicit constraints across model semantics, spatial pipeline, RTL/Chisel modules, stream protocol, memory/runtime layout, verification traces, and backend reports are easily lost, making failures hard to detect, localize, and repair.**

中文：

> **本文解决的是 agentic LLM spatial accelerator 设计中的跨层一致性问题：当 LLM agent 将 decoder-only Transformer block 转换成可部署 FPGA artifact 时，模型语义、空间流水、RTL/Chisel、stream 协议、memory/runtime layout、验证 trace 和后端报告之间的隐式约束容易丢失，导致错误难以及时发现、准确定位和最小修复。**

## 9. 最简单的理解方式

你现在可以这样理解：

> **Allo/StreamTensor 关心：如何把计算变成高效 spatial/dataflow accelerator。**
> **GPT4AIGChip/RTLSquad 关心：如何让 LLM 生成或优化硬件代码。**
> **Design Conductor 关心：agent 能不能把复杂芯片做出来。**
> **我们关心：agent 在做 LLM spatial accelerator 的过程中，如何始终知道“这个设计应该满足哪些跨层约束”，并在出错时知道“哪个约束坏了、应该最小修哪里”。**

这就是你们的问题定义。
